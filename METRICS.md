### 2.2 What actually happened, in both directions

**The original two biases (Run 2's confusion pattern) are fully resolved.**
Every code that was previously misread as "customer-fixable card issue →
unrecoverable" or "technical/unclear decline → wait and retry" now sits at
100% match: `card_expired`, `card_disabled_for_online_payments`,
`debit_instrument_inactive`, `incorrect_cvv`, `payment_timed_out`,
`gateway_technical_error`, `bank_technical_error`,
`transaction_limit_exceeded` all moved from Run 2's confusion table
straight to 100%.

**A new, different bias appeared in Run 3, on three codes that were fine
or middling before:** `authentication_failed`, `card_declined`, and
`payment_failed` — all `bank`- or `customer`-sourced declines whose
description reads like a generic "declined by the bank" rather than an
infra outage — are now proposed as `immediate_retry` or `delayed_retry`
instead of the correct `payment_link_nudge`, every time they're wrong:

```json
{
  "authentication_failed": { "delayed_retry": 16 },
  "card_declined":         { "immediate_retry": 6, "delayed_retry": 5 },
  "payment_failed":        { "immediate_retry": 5 },
  "debit_instrument_blocked": { "no_action_fraud": 1 }
}
```

**Most likely cause** (a reasoned theory, not independently re-verified
against the model's raw reasoning text for every case): the ordered rule
added in the fix says a `bank`/`gateway`/`network`-sourced decline that's
"a system/infrastructure failure" should retry immediately — the model
appears to be pattern-matching on the *source* field alone rather than
requiring the description to actually describe downtime/timeout, so a
plain "declined by the customer's bank" gets treated the same as
"bank experienced downtime." This wasn't visible before fixing the
original two biases, since Run 2's own confusion pattern was dominated by
a different failure mode entirely — a genuine example of a fix changing
*which* failure mode dominates, not just how much failure there is.

**Net result:** a large, real improvement (46%→22% override rate) with an
honestly-disclosed new failure surface on 3 of 15 codes, left unfixed in
this pass rather than iterated on further or hidden.

## 5. Gate hard-block behavior

Per `gate.py`: `MAX_ACTION_AMOUNT_PAISE` = ₹50,000/action, `MAX_RUN_TOTAL_PAISE`
= ₹5,00,000/run.

- **Subscription-recovery run:** 0 hard blocks. Every one of the 150 synthetic
  records was well under the per-action cap, and the run total (₹144,253.79
  executed) never approached ₹5,00,000. This means the cap has **never
  fired** in the subscription pipeline — it's implemented and unit-tested
  (`tests/test_gate.py`), but not demonstrated against real batch data.
- **Route demo run (`route_demo.py`), separate scenario:** 5 transfers
  attempted, **1 blocked** — `sub_route_demo_004`, reason logged verbatim
  as *"Amount 550000.00 exceeds per-action cap of 50000.00"* — an
  attempted ₹5,50,000.00 transfer correctly blocked against the
  ₹50,000.00 per-action cap. This is the only real evidence in the whole
  project of the spending cap actually intercepting an oversized action —
  worth highlighting in the pitch over the subscription pipeline's
  0-blocks number, which only proves the cap didn't get in the way, not
  that it works.

## 6. Idempotency

**Untested at the only scale that matters.** No `subscription_id` repeats
across the 150 synthetic records by construction (`generate_data.py`
generates unique IDs), so the idempotency check has never fired outside
`tests/test_gate.py`'s unit tests. `RESULTS.md`'s "Hard-blocked: 0" should
not be read as proof idempotency works under real conditions — it's
absence of a scenario that would have exercised it, not a passed test at
scale. This is disclosed in `BUILD_LOG.md` §12; repeated here since it
directly affects how the "0 hard-blocked" number should be interpreted.

## 8. What these numbers do and don't prove

- **Do prove:** the gate is load-bearing (even post-fix, a 22% override
  rate is not negligible), the audit log is complete and internally
  consistent (every count here ties out exactly to `RESULTS.md`'s
  independently-written summary), the model has specific, nameable
  failure patterns rather than random noise, both before AND after a fix
  (§2.2) — including a fix's own side effects, which were not assumed
  away but found by actually re-running the batch.
- **Don't prove:** real-world revenue recovery (everything is simulated),
  the spending cap working under real load (0 fires in 150 records), or
  idempotency working under real load (0 duplicate IDs in the test set).
